# Hold types: how the labels reach the app (#63)

*2026-11-06, first version. A proposal for the maintainer's decision.*

The hold-type labels ([#63](https://github.com/CruxCoach/CruxCoach/issues/63)) have to reach every phone. They
must be signed like everything else the app trusts, work offline, and be easy to correct when reviews find mistakes.
This report compares three ways and recommends one.

## What has to be shipped

One file per board with one entry per placement: type, second use, size class, direction, foot only, footprint, a
confidence and a source per field, the board size whose image shows the hold best, and the review flags. There are
no images and no climbs, only labels keyed by the placement ids the app already has.

| | Placements | JSON as in the test build | Compressed |
|---|---:|---:|---:|
| Kilter | 1,191 | 413 KB | 16 KB |
| All supported boards (estimate) | about 9,000 | about 3 MB | about 120 KB |

The estimate counts every placement of Tension, Grasshopper, Decoy, So iLL, Touchstone and Shiny Wall, and the
MoonBoard hold setups. Shorter keys and codes for the sources would cut the raw size to about a third. The APK stores
assets compressed, so the download grows by roughly the compressed size.

## Three ways

### A: a file in the app (like the board geometry)

`assets/hold_types/<board>.json`, read on demand into a small in-memory index.

- **Size:** about 120 KB compressed in the APK once all boards are labelled.
- **Update path:** with each app release. Test builds carry the newest labels for review.
- **Signing:** covered by the APK signature; no new trust path.
- **Offline:** always there, also for users who never download a catalogue.
- **Downside:** a correction waits for the next release.

### B: a chunk in the signed catalogue manifests

A new chunk type per board, next to the climbs and stats, verified like every chunk (manifest key, event id,
signature, chunk SHA-256).

- **Size:** negligible next to the catalogues.
- **Update path:** daily, independent of app releases.
- **Signing:** the manifest key the app already trusts.
- **Downsides:**
  - It needs a change to the catalogue pipeline.
  - Users who skip a board's catalogue would not get the labels unless the app fetches that chunk separately.
  - The labels would be tied to the release rhythm of the climb data.

### C: both, with the file in the app as the baseline

The app ships the file (A). A newer version may later come as a manifest chunk (B) and replaces the bundled one only
when its version is higher. This is how the board geometry already works: bundled seed first, a later catalogue
import replaces it.

### Side by side

| | A: in the app | B: in the manifests | C: both |
|---|---|---|---|
| Works without a catalogue | yes | no | yes |
| Corrections reach users | with a release | next day | next day, once B exists |
| Pipeline change | no | yes | later |
| New trust path | no | no (same manifest key) | no |
| Work now | small | medium | small now, medium later |

## Recommendation

**A now, C later.** Ship the labels as a file in the app, as the test build already does. Add the manifest chunk
when reviews produce corrections faster than releases ship, which is probably once Kilter, MoonBoard and Tension
are labelled and the review screen is open to everyone.

Further notes:

- **No schema change.** The labels are read from the file. The stats can compute a problem's hold types from its
  frames on the fly.
- **Filter.** A hold-type filter over a whole catalogue, which can be some 250,000 problems, may later need a
  precomputed column. That would be a database change and comes to the maintainer first.
- **Format.** The format is versioned: `format` names the schema, `version` the label set. The app ignores a file
  whose format it does not know.
